这是一条很强的环境初始化线索，但在没有额外探针或 Gateway 启动日志的情况下，不应该把它扩大成 “Gateway 一定读取了 .zshenv” 这样的结论。

因此，本次问题更准确的根因描述是：

JetBrains Remote Backend 启动时获得的环境中缺少 nvm 当前 Node 的 bin 目录，由 Remote Backend 启动的 Java 应用也继承了这套缺少 Node 的 PATH。

SSH 中 node -v 正常并不能否定这个结论，因为 nvm 本身就是 per-user、per-shell 的版本管理器。一个 Shell 能找到 Node，不代表另一个已经启动的进程具有完全相同的 PATH。(GitHub)

处理方向也随之变得清楚：让 Node 环境进入 Remote Backend 能继承到的启动环境，重新创建 Backend，再以 /proc/<pid>/environ、Java 的 System.getenv("PATH") 和实际 node -v 执行结果完成验证。
